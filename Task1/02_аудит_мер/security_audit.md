# Аудит безопасности данных компании «Медикаменте» (As-Is)

## 1. Введение

### 1.1. Назначение документа

Данный документ содержит результаты аудита мер по обеспечению безопасности данных в компании «Медикаменте». Аудит проведён на основе анализа текущей архитектуры (As-Is), выявленных конфиденциальных данных и диаграмм потоков данных (DFD).

Аудит безопасности является связующим звеном между анализом As-Is и проектированием мер защиты. Если анализ As-Is отвечает на вопрос «что мы имеем», а реестр данных — «что защищаем», то аудит безопасности отвечает на вопросы «где уязвимости» и «какие риски». Результаты этого аудита напрямую определяют приоритеты внедрения мер защиты в целевой архитектуре (To-Be).

### 1.2. Цели аудита

Проведение аудита безопасности преследует следующие цели:
- **Выявление уязвимостей** — обнаружение слабых мест в текущей архитектуре
- **Оценка рисков** — определение вероятности и потенциального ущерба от инцидентов
- **Анализ соответствия** — проверка выполнения требований 152-ФЗ
- **Определение приоритетов** — ранжирование уязвимостей для планирования работ

### 1.3. Критерии аудита

Аудит проведён на основе следующих критериев и стандартов:

**Законодательные требования:**
- Требования 152-ФЗ «О персональных данных» — федеральный закон, регулирующий обработку ПДн в РФ
- Требования Privacy By Design — принципы встраивания защиты приватности на этапе проектирования

**Принципы защиты данных:**
- Принцип Data Minimization — сбор и обработка только минимально необходимых данных
- Принцип Purpose Limitation — использование данных только для заявленных целей
- Принцип Storage Limitation — хранение данных не дольше необходимого срока

**Отраслевые стандарты:**
- ISO 27001 — международный стандарт информационной безопасности
- NIST Cybersecurity Framework —框架 кибербезопасности Национального института стандартов США

## 2. Методология аудита

### 2.1. Подход к аудиту

Аудит безопасности компании «Медикаменте» проведён с использованием процессно-ориентированного подхода. Вместо проверки отдельных систем или технологий мы анализируем безопасность в контексте бизнес-процессов. Это позволяет:
- Выявить уязвимости в точках взаимодействия между системами
- Оценить риски для каждого этапа обработки данных
- Определить владельцев рисков (ответственных за процессы)

### 2.2. Направления аудита

Аудит проведён по следующим семи направлениям:

1. **Хранение данных** — как и где хранятся конфиденциальные данные
   - Оценка защищённости хранилищ
   - Проверка шифрования at rest
   - Анализ резервного копирования

2. **Передача данных** — как данные перемещаются между системами
   - Оценка защищённости каналов связи
   - Проверка шифрования in transit
   - Анализ протоколов передачи

3. **Контроль доступа** — кто имеет доступ к данным
   - Проверка аутентификации
   - Оценка авторизации (RBAC/ABAC)
   - Анализ привилегированных учётных записей

4. **Шифрование** — используются ли механизмы шифрования
   - Оценка алгоритмов шифрования
   - Проверка управления ключами
   - Анализ охвата шифрованием

5. **Аудит и мониторинг** — логируются ли операции с данными
   - Проверка полноты логирования
   - Оценка системы алертинга
   - Анализ возможностей расследования инцидентов

6. **Резервное копирование** — есть ли backup данных
   - Проверка стратегии бэкапов
   - Оценка тестирования восстановления
   - Анализ гео-распределения копий

7. **Соответствие законодательству** — выполнение требований 152-ФЗ
   - Проверка технических мер защиты
   - Оценка организационных мер
   - Анализ документации

### 2.3. Шкала оценки рисков

Для оценки выявленных уязвимостей используется следующая шкала рисков:

| Уровень риска | Описание | Требуемая реакция |
|---------------|----------|-------------------|
| **Критический** | Непосредственная угроза утечки, нарушение 152-ФЗ | Немедленное устранение (P0) |
| **Высокий** | Высокая вероятность инцидента, серьёзный ущерб | Устранение в течение 2 недель (P1) |
| **Средний** | Умеренный риск, ограниченный ущерб | Планирование в ближайшем спринте (P2) |
| **Низкий** | Минимальный риск, незначительный ущерб | Устранение по возможности (P3) |

## 3. Результаты аудита по процессам

В этом разделе представлены детальные результаты аудита для каждого из шести бизнес-процессов компании «Медикаменте». Для каждого процесса проведён анализ по семи направлениям методологии (хранение, передача, контроль доступа, шифрование, аудит, резервное копирование, соответствие).

По итогам аудита каждого процесса выявлены конкретные уязвимости с присвоением уникальных идентификаторов (U001, U002, ...). Сводный список всех уязвимостей с оценкой рисков представлен в разделе 4.

### 3.1. Процесс: Запись пациента к врачу

**Контекст процесса:** Запись пациента к врачу — первая точка контакта клиента с информационной системой клиники. На этом этапе собираются первичные персональные данные (ФИО, телефон), которые требуют защиты в соответствии с 152-ФЗ. Процесс полностью ручной, что создаёт дополнительные риски человеческих ошибок и несанкционированных изменений.

| Аспект | Текущее состояние | Проблема | Риск |
|--------|-------------------|----------|------|
| Хранение | Excel-файлы на файловом сервере | Нет шифрования, доступ по правам NTFS | Высокий |
| Передача | Локальная сеть, SMB | Данные передаются в открытом виде | Средний |
| Контроль доступа | Доменная аутентификация Windows | Нет разграничения по ролям | Высокий |
| Шифрование | Отсутствует | Файлы читаются любым пользователем домена | Критический |
| Аудит | Не настроен | Невозможно отследить, кто открывал файл | Высокий |

**Уязвимости:**
- U001: Excel-файлы с ПИИ доступны всем сотрудникам домена
- U002: Нет логирования доступа к журналам записей
- U003: Резервное копирование не настроено или не документировано

---

### 3.2. Процесс: Ведение медицинской карты

**Контекст процесса:** Ведение медицинской карты — центральный процесс формирования и накопления конфиденциальной медицинской информации о пациенте. Медицинские данные относятся к специальной категории персональных данных и требуют максимальной защиты согласно 152-ФЗ. Утечка диагнозов или результатов анализов может нанести непоправимый репутационный ущерб пациенту и привести к серьёзным штрафам для клиники.

| Аспект | Текущее состояние | Проблема | Риск |
|--------|-------------------|----------|------|
| Хранение | Папки на файловом сервере (JPG, PDF, XLSX) | Нет шифрования, нет версионности | Критический |
| Передача | Копирование файлов по сети | Перехват трафика | Средний |
| Контроль доступа | Общий доступ к папкам | Все врачи видят все карты | Критический |
| Шифрование | Отсутствует | Медицинские данные в открытом доступе | Критический |
| Аудит | Не настроен | Невозможно отследить утечку | Высокий |

**Уязвимости:**
- U004: Медицинские карты доступны всем сотрудникам без разграничения
- U005: Нет разделения доступа по лечащим врачам
- U006: Отсутствует шифрование медицинских данных (требование 152-ФЗ)
- U007: Нет возможности отследить, кто просматривал карту

### 3.3. Процесс: Оплата медицинских услуг

**Контекст процесса:** Процесс оплаты затрагивает как персональные данные пациентов, так и финансовую информацию о транзакциях. Хотя финансовые данные менее чувствительны, чем медицинские, их утечка может привести к финансовому мошенничеству. Кроме того, связь между пациентом и суммой платежа может косвенно раскрыть информацию о полученных услугах.

| Аспект | Текущее состояние | Проблема | Риск |
|--------|-------------------|----------|------|
| Хранение | Excel + 1С:Бухгалтерия (файловый режим) | Файл 1С доступен на чтение | Высокий |
| Передача | OLE между ККМ и 1С | Локальный протокол, риск перехвата | Низкий |
| Контроль доступа | Учётные записи 1С | Нет детализации прав | Средний |
| Шифрование | Отсутствует | Финансовые данные в открытом виде | Средний |
| Аудит | Встроенный аудит 1С (ограниченный) | Не покрывает все операции | Средний |

**Уязвимости:**
- U008: Файловый режим 1С не обеспечивает надёжную защиту
- U009: Нет разграничения прав внутри 1С по кассирам
- U010: Журнал аудита 1С не настроен на критичные операции

### 3.4. Процесс: Учёт ТМЦ

**Контекст процесса:** Учёт ТМЦ обеспечивает контроль за движением медикаментов, оборудования и расходных материалов. Хотя данные о ТМЦ не относятся к персональным, информация о стоимости и поставщиках представляет коммерческую ценность. Утечка данных о поставщиках может быть использована конкурентами.

| Аспект | Текущее состояние | Проблема | Риск |
|--------|-------------------|----------|------|
| Хранение | 1С:Торговля и склад (файловый режим) | Аналогично 1С:Бухгалтерия | Средний |
| Передача | OLE между 1С:ТиС и 1С:Бух | Внутренний трафик | Низкий |
| Контроль доступа | Учётные записи 1С | Базовый уровень | Средний |
| Шифрование | Отсутствует | Данные о стоимости в открытом виде | Низкий |
| Аудит | Встроенный аудит 1С | Ограниченный | Средний |

**Уязвимости:**
- U011: Нет разграничения доступа к данным о поставщиках
- U012: Синхронизация между 1С не логируется детально

### 3.5. Процесс: Лабораторные анализы

**Контекст процесса:** Лабораторные анализы — процесс с внешним контуром, так как биоматериал и направления передаются за пределы информационной системы. Результаты анализов относятся к медицинской тайне и требуют особой защиты. Процесс включает как физическую передачу биоматериала, так и электронную регистрацию результатов.

| Аспект | Текущее состояние | Проблема | Риск |
|--------|-------------------|----------|------|
| Хранение | Excel-реестры + папки пациентов | Нет шифрования, нет контроля | Критический |
| Передача | Бумажные носители + файлы | Потеря, утечка | Высокий |
| Контроль доступа | Общий доступ к папке Laboratory Registry | Все видят все анализы | Критический |
| Шифрование | Отсутствует | Результаты анализов — особая категория ПДн | Критический |
| Аудит | Не настроен | Невозможно отследить доступ | Высокий |

**Уязвимости:**
- U013: Результаты анализов доступны всем сотрудникам
- U014: Нет разграничения по пациентам и врачам
- U015: Передача результатов пациенту не логируется

### 3.6. Процесс: Бухгалтерский учёт

**Контекст процесса:** Бухгалтерский учёт включает обработку платежей пациентов, кадровый учёт сотрудников, начисление зарплат и подготовку налоговой отчётности. Этот процесс концентрирует наиболее чувствительные финансовые данные — зарплаты сотрудников, которые являются коммерческой тайной.

| Аспект | Текущее состояние | Проблема | Риск |
|--------|-------------------|----------|------|
| Хранение | 1С:Бухгалтерия (файловый режим) | Файл базы доступен | Высокий |
| Передача | Внутренние вызовы OLE | Локально | Низкий |
| Контроль доступа | Учётные записи 1С | Нет детализации | Средний |
| Шифрование | Отсутствует | Зарплаты, персональные данные сотрудников | Высокий |
| Аудит | Встроенный аудит 1С | Не покрывает всё | Средний |

**Уязвимости:**
- U016: Зарплаты сотрудников видны всем бухгалтерам
- U017: Паспортные данные сотрудников не зашифрованы
- U018: Нет разграничения доступа к кадровым данным

## 5. Анализ соответствия 152-ФЗ

### 5.1. Требования по шифрованию (Ст. 19)

Статья 19 152-ФЗ устанавливает требования к защите персональных данных при их обработке. В частности, оператор ПДн обязан применять меры шифрования, разграничения доступа и аудита. Ниже представлена оценка выполнения этих требований в компании «Медикаменте».

| Требование | Статус | Комментарий |
|------------|--------|-------------|
| Шифрование ПДн при хранении | ❌ Не выполнено | Все данные в открытом виде |
| Шифрование ПДн при передаче | ❌ Не выполнено | Локальная сеть без шифрования |
| Разграничение доступа | ❌ Не выполнено | Нет RBAC/ABAC |
| Учёт обращений к ПДн | ❌ Не выполнено | Аудит не настроен |

### 5.2. Требования по локализации (Ст. 18)

Статья 18 152-ФЗ требует, чтобы обработка персональных данных осуществлялась на территории Российской Федерации. Это требование направлено на обеспечение контроля за обработкой ПДн со стороны российских регуляторов.

| Требование | Статус | Комментарий |
|------------|--------|-------------|
| Хранение на территории РФ | ✅ Выполнено | Сервер в офисе компании |
| Обработка на территории РФ | ✅ Выполнено | Все процессы локально |

**Вывод:** Требования локализации выполняются, так как вся ИТ-инфраструктура компании находится в офисе на территории РФ.

### 5.3. Требования по согласию (Ст. 6, 9)

Статьи 6 и 9 152-ФЗ регулируют получение согласия субъекта ПДн на обработку его персональных данных. Оператор обязан получить письменное согласие, а также предоставить субъекту право на отзыв согласия и доступ к своим данным.

| Требование | Статус | Комментарий |
|------------|--------|-------------|
| Получение согласия на обработку | ⚠️ Не документировано | Требуется проверка |
| Право на отзыв согласия | ❌ Не реализовано | Нет процедуры удаления |
| Право на доступ к своим данным | ⚠️ Частично | Пациент может запросить файлы |

**Вывод:** Требуется документирование процесса получения согласий и реализация процедуры удаления данных по отзыву согласия.

### 5.4. Privacy By Design

Privacy By Design (PbD) — концепция встраивания защиты приватности на этапе проектирования системы, а не добавления её постфактум. Семь принципов PbD являются международным стандартом для систем, обрабатывающих персональные данные.

| Принцип | Статус | Комментарий |
|---------|--------|-------------|
| Минимизация данных | ❌ Не применяется | Собираются избыточные данные |
| Ограничение цели | ⚠️ Частично | Данные используются по назначению |
| Ограничение хранения | ❌ Не применяется | Нет политик удаления |
| Точность данных | ⚠️ Частично | Ручной ввод, возможны ошибки |
| Конфиденциальность | ❌ Не обеспечена | Нет шифрования и контроля |

**Вывод:** Принципы Privacy By Design не применяются в текущей архитектуре. Требуется внедрение PbD в целевой архитектуре (To-Be).

## 6. Оценка рисков

### 6.1. Матрица рисков

На основе выявленных уязвимостей проведена оценка рисков информационной безопасности. Риск оценивается по двум параметрам: вероятность реализации угрозы и потенциальное влияние на бизнес. Комбинация этих параметров определяет итоговый уровень риска.

| Риск | Вероятность | Влияние | Уровень |
|------|-------------|---------|---------|
| Утечка медицинских данных | Высокая | Критическое | **Критический** |
| Утечка ПИИ пациентов | Высокая | Высокое | **Высокий** |
| Утечка зарплат сотрудников | Средняя | Высокое | **Высокий** |
| Потеря данных (нет backup) | Средняя | Критическое | **Высокий** |
| Штрафы от Роскомнадзора | Средняя | Высокое | **Высокий** |
| Репутационные потери | Средняя | Критическое | **Высокий** |
| Несанкционированное изменение | Низкая | Высокое | **Средний** |

**Интерпретация рисков:**
- **Критический риск** (утечка медицинских данных) — требует немедленного вмешательства руководства
- **Высокие риски** — должны быть устранены в приоритетном порядке в течение 2-4 недель
- **Средние риски** — требуют планирования и включения в дорожную карту безопасности

## 7. Проблемные зоны (сводный список)

На основе аудита безопасности сформулированы девять ключевых проблемных зон. Проблемы сгруппированы по уровням критичности: критические (требуют немедленного устранения), высокие (требуют устранения в течение 2 недель) и средние (требуют планирования).

### 7.1. Критические проблемы

Эти проблемы создают непосредственную угрозу утечки данных и нарушения 152-ФЗ. Устранение должно быть начато немедленно.

1. **Отсутствие шифрования конфиденциальных данных**
   - Медицинские данные хранятся в открытом виде
   - ПИИ пациентов не зашифрованы
   - Зарплаты сотрудников доступны в открытом виде

2. **Отсутствие разграничения доступа**
   - Все сотрудники видят все медицинские карты
   - Нет принципа минимальных привилегий
   - Нет RBAC/ABAC

3. **Отсутствие аудита операций**
   - Невозможно отследить, кто просматривал данные
   - Нет алертинга на подозрительные действия
   - Журналы 1С не покрывают все операции

### 7.2. Высокие проблемы

Эти проблемы создают высокий риск инцидентов безопасности и должны быть устранены в течение 2-4 недель.

4. **Файловый режим хранения**
   - Excel-файлы на общем диске
   - 1С в файловом режиме
   - Нет СУБД с транзакциями

5. **Отсутствие резервного копирования**
   - Нет документированной стратегии backup
   - Нет тестирования восстановления

6. **Невыполнение 152-ФЗ**
   - Нет шифрования (требование Ст. 19)
   - Нет учёта обращений (требование Ст. 18.1)
   - Нет процедуры удаления данных

### 7.3. Средние проблемы

Эти проблемы влияют на общую зрелость безопасности и должны быть addressed в рамках среднесрочного планирования.

7. **Избыточный сбор данных**
   - Нет принципа Data Minimization
   - Собираются данные «про запас»

8. **Отсутствие политик хранения**
   - Нет сроков хранения данных
   - Нет процедуры уничтожения

9. **Ручная обработка данных**
   - Много ручного ввода
   - Риск ошибок и утечек

## 8. Рекомендации по приоритетам

### 8.1. Дорожная карта устранения уязвимостей

На основе оценки рисков сформулированы приоритетные рекомендации по устранению выявленных уязвимостей. Рекомендации сгруппированы по четырём приоритетам (P0-P3) с указанием рекомендуемых сроков реализации.

### Приоритет P0 (Немедленно)

Меры, необходимые для немедленного снижения критических рисков. Реализация должна быть начата в течение 1 недели.

1. Внедрить шифрование для медицинских данных и ПИИ
2. Реализовать разграничение доступа (RBAC)
3. Настроить аудит всех операций с конфиденциальными данными

### Приоритет P1 (В течение месяца)

Меры, необходимые для выполнения требований 152-ФЗ и снижения высоких рисков.

4. Перейти на клиент-серверную СУБД (PostgreSQL)
5. Настроить резервное копирование
6. Внедрить механизм тегирования данных

### Приоритет P2 (В течение квартала)

Меры, направленные на повышение общей зрелости безопасности.

7. Разработать политики хранения и удаления данных
8. Автоматизировать сбор данных (уменьшить ручной ввод)
9. Внедрить маскирование данных при отображении

### Приоритет P3 (В течение года)

Стратегические меры для долгосрочного развития системы безопасности.

10. Полный переход на Privacy By Design
11. Сертификация по ISO 27001
12. Регулярные пентесты и аудиты безопасности

## 9. Выводы

### 9.1. Общая оценка состояния безопасности

**Текущее состояние безопасности:** **Неудовлетворительное**

Компания «Медикаменте» имеет **критические уязвимости** в области защиты конфиденциальных данных:

- ❌ Выявлено **18 уязвимостей**, из них **5 критических**, **7 высоких**
- ❌ Не выполнены ключевые требования **152-ФЗ** (шифрование, аудит, разграничение доступа)
- ❌ Не применены принципы **Privacy By Design**
- ❌ Высокий риск **утечки данных**, **штрафов от Роскомнадзора** и **репутационных потерь**

### 9.2. Необходимые действия

**Необходимы немедленные действия** по устранению критических уязвимостей и приведению системы в соответствие с требованиями законодательства.

**Приоритетные направления:**
1. **Шифрование** — внедрение AES-256 для медицинских данных и ПИИ
2. **Контроль доступа** — реализация RBAC/ABAC для разграничения доступа
3. **Аудит** — логирование всех операций с конфиденциальными данными
4. **Архитектура** — переход на клиент-серверную СУБД (PostgreSQL)

Детальные меры защиты и архитектура To-Be представлены в документе [protection_measures.md](../03_улучшения/protection_measures.md).
